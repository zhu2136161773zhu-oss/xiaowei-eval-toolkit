## 这是什么

2026 全国大学生软件测试大赛「微信小微 AI 助手评测专项赛」的配套评测工具。

官方培训明确了两条对参赛者极其有利的规则：

| 规则 | 官方原话 |
|:--|:--|
| ✅ 允许 | 「用自动化框架生成上万条输入、只挑异常案例提交」 |
| ✅ 允许 | 「在报告中展示技术实现与实际效果」——**且可直接提升「创新与方法论」评分** |
| ⛔ 红线 | 外部工具打线上 **QPM 不宜超过 16** |
| ⛔ 红线 | 严禁注入黄反暴政等违规内容，有封号风险 |

本工具包正是围绕这两条规则设计的：**把有限的体验时间（11/1–11/5）产出尽可能多的有效案例，同时保证不越线。**

### 为什么需要它

初赛只有 11 天（11/6–11/13 提交），而小微的评测要覆盖官方推荐的「复合需求 / 变参测试 / 多轮改条件 / 边界探测」四条打法。纯手工测试的问题是：

- 一天最多测 30–50 条，覆盖不了变参空间
- 人眼很难发现「上下文污染」「状态串台」这类隐蔽缺陷
- 报告的「原因分析」一栏容易写成「可能是上下文问题」这种猜测

本工具包解决这三点。

## 快速开始

### 环境要求

- Python 3.8+（Windows / macOS / Linux）
- 核心功能**零第三方依赖**即可运行
- 可选：`pip install -r requirements.txt` 解锁 Word 报告与安卓自动化

```bash
git clone https://github.com/your-name/xiaowei-eval-toolkit.git
cd xiaowei-eval-toolkit
```

### 三条命令

```bash
# ① 生成用例（场景可选 A/B/C/D/E/F 或 all）
python pipeline.py gen --suite A

# ② 采集（脚本把指令放进剪贴板，你粘贴给小微，复制回复回来）
python pipeline.py run --suite A --mode manual

# ③ 自动筛查 + 出报告
python pipeline.py report --raw data/raw_A.jsonl --suite A
python pipeline.py report --raw data/raw_A.jsonl --suite A --docx   # 出 Word
```

│      └── data/raw_*.jsonl   每轮对话结构化落盘

│      │

### 四种采集模式

| 模式 | 命令 | 场景 | 说明 |
|:--|:--|:--|:--|
| 半自动 | `--mode manual` | 零配置 | 每条指令进剪贴板 → 粘贴给小微 → 复制回复回来。**今晚就能跑** |
| 持续循环 | `--mode loop --rounds 5` | 复现性验证 | 同一批反复问，验证官方第五条「能稳定复现」，抓偶现问题频率 |
| 安卓全自动化 | `--mode uia2 --serial <设备号>` | 批量扫描 | 荣耀手机开 USB 调试，自动输入、自动等待、自动截图 |
| PC 微信 | `--mode pc` | 仅辅助 | ⚠️ 官方明示 PC 端功能残缺，落后移动端 1–2 个版本 |

## 自动异常检测器

这是本工具包的核心技术实现。八类规则**全部基于小微实测暴露的真实缺陷模式**设计，不是泛泛而谈的关键词匹配。

| 检测类型 | 抓什么 | 严重度 |
|:--|:--|:--:|
| 上下文污染 | 本轮回复出现前序任务的文本片段（n-gram 交叉比对） | 高 / 中 |
| **品类串台** | 本轮任务不涉及该品类，回复却带着前序品类的结果（语义级） | 高 |
| 状态隔离失效 | 本轮回复与历史用例的回复高度重合，草稿/上下文未隔离 | 高 |
| 约束丢失 | 指令给了预算、人数、附近、时间，回复里完全没体现 | 中 / 低 |
| 模糊失败话术 | 把失败归给「接口 / 系统 / 检索结果」，而非坦承能力不足 | 中 |
| 数值幻觉 | 回复出现指令里根本不存在的具体数值 | 中 |
| 答案翻转 | 先给出正确答案，被用户错误质疑后改口 | 高 |
| 越界宣称 | 对官方明示不支持的能力却说「可以 / 支持」 | 高 |

### 两个值得写进报告的设计细节

这两点本身就是「创新与方法论」的加分内容：

**① 跨会话滚动语料**

状态串台检测的关键在于：串台内容常常来自**「上一次测试」**，而不是同一条用例内部。所以检测器维护一份跨会话的滚动语料库，比对范围覆盖全部历史用例。

```
历史用例 H-001 的回复「可以出发了」
        ↓ 滚动语料累积
本轮指令「跟光头强说今天不想加班，语气委婉一点」
本轮回复「可以出发了」
        ↓
命中 state_leak，相似度 1.00
```

**② 品类同义词映射**

纯字面比对抓不到语义级串台。前一轮点的是「瑞幸生椰拿铁」，本轮搜「火锅」却返回「咖啡相关的小程序」——字面 n-gram 完全不重合，但在品类层面能识别出这是上下文污染。

```python
CATEGORY_SYNONYMS = {
    "咖啡": ["咖啡", "瑞幸", "生椰拿铁", "拿铁", "美式", "摩卡", "星巴克"],
    "火锅": ["火锅", "海底捞", "呷哺", "凑凑"],
    ...
}
```

### 检测器输出的是「可疑」，不是「结论」

每条命中都附带**初步归因建议**，例如：

> 上下文污染：建议把该子任务单独发给小微，若单发正常，则问题定位在复合指令的任务编排层，而非该能力本身。

最终定性仍由人工把关——这符合官方「基于控制变量与差分测试形成的因果推断证据」的判定要求。

## 对照实验设计

官方答疑明确认可控制变量与差分测试的因果推断证据。以下三组对照是报告里最有说服力的部分。

### 对照一：单发 vs 复合下发

```
同一条指令单独发给小微  →  记录结果
再把它放进复合指令里    →  记录结果
```

**若单发正常、复合失败 → 问题定位在任务编排层，而非该能力本身。** 这是归因的关键一步，也是把「小微表现不佳」升级成「可修复的具体环节」的唯一路径。

### 对照二：开记忆 vs 关记忆

- 用两个微信号：A 开记忆、B 关记忆
- 每次测完**立即长按删除对话**，清空记忆库、RAG 库与上下文，避免污染后续实验
- 同一用例在两个账号各跑一次，差异即为记忆带来的影响

### 对照三：清空上下文 vs 保留上下文

- 测完立即长按删除对话 → 重发同一条指令
- 若结果不同，说明该问题的成因与上下文状态强相关

> 以上三组对照的结论，都可以直接写进报告的「原因分析」一节，
> 而不是停留在「可能是上下文问题」的猜测层面。

## 报告输出

`report.py` 直接按官方要求生成，每条案例都已写好六要素：

```
场景描述 → 复现步骤 → 期望小微回复的内容 → 实际结果 → 原因分析 → 改进建议
```

同时附一张**赛事表单字段对照表**（issue 名称 / 一句话总结 / 入口 / 对话总轮数 / 满意度等级 A–D / 可复现性 / 建议复现步骤 …），逐项填好，只需复核和补截图。

报告里的「原因分析」会模仿官方给的归因示例，给出**具体机制推测**而非空泛判断：

> 问题类型判定为「上下文污染 / 任务编排缺陷」。
> 初判依据：建议把该子任务单独发给小微，若单发正常，则问题定位在任务编排层。
> 结合官方对「任务失败只有两种可能」的判定框架——本条属于「功能存在但没做好」，
> 即 Bad Case；而非「能力本身有边界」的有价值洞察。

## 进阶：拿「创新与方法论」高分

### 一、批量变参扫描

把某个变量在 20 种取值上跑一遍，找出「在哪个取值上开始出错」的临界点。这类**失效边界定位**是普通参赛者很难交付的东西。

### 二、差分测试与因果归因

固定其他条件，只变一个因子，观察输出差异。官方答疑明确认可这种方法形成的因果推断证据。

### 三、自动化评分器的一致性检验

官方在答疑中透露，他们自己就用**多个不同大模型作为评审器**，通过多评审一致性检验（IAA、卡帕值 Kappa）压制系统性偏差。

你可以把自己的自动检测器用同样的方法做一次一致性验证——让两个不同模型各自独立判断一批样本，报告 Kappa 值。这一节写进报告，是「创新与方法论」评分项里最有说服力的内容。

## 合规声明

本工具包严格遵守赛事规则与红线：

- **QPM ≤ 16**（默认 8，超过 16 强制降速并告警），绝不以压测方式冲击线上
- **不注入任何违规内容**，工具包内无此类功能
- **真实采集数据不入库**：`.gitignore` 已排除 `data/raw_*.jsonl` 与截图目录，
  因为采集结果含你与微信好友的**真实对话内容**，涉及他人隐私
- 官方承诺「隐私案例会在沙箱环境中用改写后的对话复现，不会直接使用你提交的私人聊天记录」，
  本工具包同样遵循这一原则
- 官方提醒「AI 工具生成的内容仅供参考，评测报告禁止由 AI 全权代写」——
  本工具包产出的是**待复核的候选案例与归因建议**，最终判断与报告撰写由人完成
